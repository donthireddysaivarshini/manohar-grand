# Cancellation & Refund Policy Engine

> [!IMPORTANT]
> **Phase Notice**: This document details the policy engine architecture for **Phase 4 & Phase 5**. Cancellation and refund execution must **NOT** be implemented in Phase 1.

---

## 1. Client-Confirmed Business Baseline

### 1.1 Confirmed Policy Rules:
1. **Strict Non-Refundable Policy**:
   - Once a booking is confirmed and advance payment is received, the booking **cannot be cancelled** and there is **no refund** (0% refund).
2. **Same-Day Cancellation / No-Show**:
   - Strictly **Non-Refundable (0% Refund)**.
3. **Payment & Confirmation Terms**:
   - Online bookings require a 50% advance deposit via Razorpay.
   - The remaining 50% is payable at the hotel before check-in.
   - Once confirmed with the advance payment, the reservation is final and non-refundable.

---

## 2. Configurable Policy Engine Architecture

Even though the current client rule is strict non-refundability (0%), the business rules must **never be hardcoded** into frontend components.

The backend implements a dynamic, centrally configurable policy engine (`CancellationPolicy` & `CancellationPolicyRule`):

```
Table: cancellation_policy_rule
- id: UUID
- policy_id: ForeignKey(CancellationPolicy)
- min_hours_before_checkin: Integer (e.g., 0)
- max_hours_before_checkin: Integer (null / unlimited)
- refund_percentage: Decimal (Current baseline: 0.00)
- cancellation_fee_fixed: Decimal (default: 0.00)
- description: CharField ("Non-refundable once confirmed")
- is_active: Boolean
```

This guarantees that if the hotel management later introduces flexible cancellation tiers or partial refunds, the rule can be updated in the backend database without rewriting frontend booking UI code.

## 3. Cancellation & Refund Lifecycle

```
Customer / Front-Desk Initiates Cancellation Request
                |
                v
[ Authoritative Backend Policy Evaluation ]
- Checks booking status and payment records
- Evaluates active CancellationPolicyRule (Default: 0% refund)
- Computes refund entitlement from BookingPriceSnapshot
                |
    +-----------+-----------+
    |                       |
    v (0% Refund Baseline)  v (>0% Refund if Policy Updated / Manager Override)
[ Booking -> CANCELLED ]   [ Booking -> CANCELLED ]
[ Refund Record: 0 INR ]   [ Refund Record: status='requested' ]
[ Inventory Released ]     [ Inventory Released ]
                            |
                            v
                   [ Hotel Manager Review (Admin Panel) ]
                   - Verifies transaction & reason
                   - Clicks "Approve & Execute Refund" (Emergency Override)
                            |
                            v
                   [ Gateway Refund API (Phase 5) ]
                   - Initiates gateway refund
                   - Webhook confirms `refund.processed`
                   - Refund status -> PROCESSED
                   - Notification dispatched to Guest
```

---

## 4. Operational Cancellation & Override Scenarios
- **No-Show**: If guest does not arrive on the check-in date and front desk marks status as `no_show`, the reservation is closed with 0% refund and remaining stay nights are released back to unified inventory.
- **Admin Discretionary Emergency Override**: Hotel Owner/Managers retain authorization to execute an exceptional full/partial refund under force majeure or emergency maintenance. All discretionary overrides require a mandatory justification note and are recorded permanently in `AuditLog`.
