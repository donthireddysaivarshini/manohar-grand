# System Architecture & Technical Design — Manohar Grand Hotel Backend

## 1. High-Level Architectural Overview
The Manohar Grand Hotel platform follows a decoupled, headless client-server architecture:
- **Client Tier**: 
  - Customer Direct Booking Web App: React (SPA), TypeScript, Vite, Tailwind CSS, Lucide Icons.
  - Staff / Hotel Admin Panel: Purpose-built React Admin Application.
- **API Gateway / Routing Tier**: Nginx (Production) / Vite Dev Proxy (Local), RESTful API namespace `/api/v1/`.
- **Application Server Tier**: Python 3.12+, Django 5.2 LTS, Django REST Framework (DRF), Gunicorn / ASGI.
- **Database Tier**:
  - *Development & Testing*: SQLite (`db.sqlite3`) with WAL mode enabled.
  - *Production Target*: PostgreSQL 16+ with connection pooling (e.g. PgBouncer) for true row-level locking (`SELECT FOR UPDATE`) and ACID guarantees under high concurrent traffic.
- **Cache & Async Worker Tier**: Redis + Celery / background worker tasks for hold expirations (15 mins configurable) and asynchronous notification hooks.

## 2. Django Apps Modularization Strategy

To ensure high maintainability, clear separation of concerns, and clean boundary encapsulation, the backend project is organized into 8 focused Django apps:

```
backend/
├── manage.py
├── manohar_grand/               # Core Project Configuration
│   ├── __init__.py
│   ├── settings/
│   │   ├── base.py              # Shared settings, apps, middleware
│   │   ├── development.py       # SQLite, debug mode, CORS local
│   │   └── production.py        # PostgreSQL, SSL, secure cookies, Sentry
│   ├── urls.py                  # Master /api/v1/ URL router
│   ├── wsgi.py
│   └── asgi.py
├── apps/
│   ├── authentication/          # User accounts, Google OAuth (django-allauth), Staff RBAC
│   ├── rooms/                   # Room categories, 28 physical rooms, amenities, images
│   ├── inventory/               # Calendar night availability, room blocks, maintenance blocks
│   ├── bookings/                # Unified reservation engine, 15-min hold, status machine
│   ├── pricing/                 # Dynamic price calculator, tax slabs, immutable snapshots
│   ├── payments/                # Razorpay order gateway, webhook processor, refund ledger
│   ├── cms/                     # Headless CMS for marketing content, gallery, FAQs, policies
│   └── corporate/               # Bulk inquiries, custom corporate quotes
├── core/                        # Shared utilities, permissions, pagination, standard envelopes
└── tests/                       # Integration test suites & test runners
```

### App Responsibility Breakdown:
1. `apps.authentication`: Custom `User` model, `CustomerProfile`, `StaffProfile`. Google OAuth integration for customers via standard Django social-auth (`django-allauth`) with credentials (`GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`) managed via environment variables. Staff email/password authentication with PBKDF2/Argon2 hashing. Role permissions: `SUPER_ADMIN`, `MANAGER`, `RECEPTIONIST`. (NO Phone OTP / Magic Link).
2. `apps.rooms`: `RoomCategory` (AC, Non-AC), `PhysicalRoom` (authoritative 28 rooms: 20 AC, 8 Non-AC), `Amenity`, `RoomImage`. `RoomCategory.total_inventory` is strictly a derived/read-only property and never an independently editable source of truth.
3. `apps.inventory`: Authoritative night availability calculator based on active physical rooms, `RoomBlock`, `MaintenanceBlock`. `RoomNightInventory` is under architectural review as a derived occupancy ledger and will not be implemented until fully vetted.
4. `apps.bookings`: Unified reservation engine (online direct, walk-in, phone, corporate), configurable temporary checkout hold (default: 15 minutes), guest records with verification metadata, physical room assignment at check-in, booking status state machine.
5. `apps.pricing`: Base rates, configurable extra adult/child surcharge calculations, configurable tax rules (GST), immutable `BookingPriceSnapshot`.
6. `apps.payments`: `PaymentOrder`, `PaymentTransaction`, Razorpay order creation, HMAC-SHA256 signature verification, idempotent webhook processing, refund ledger.
7. `apps.cms`: Headless CMS for hero banner, welcome section copy ("Redefines Luxury with Affordable Prices"), gallery album, FAQ accordion, cancellation policies.
8. `apps.corporate`: Corporate inquiries, negotiated rate quotes, company profile bindings.

## 3. Database Strategy: SQLite vs PostgreSQL

### 3.1 SQLite for Development / Testing Only
- SQLite (`db.sqlite3`) is used exclusively for local development, prototyping, and fast test suite runs.
- WAL (Write-Ahead Logging) mode is enabled (`PRAGMA journal_mode=WAL;`) to reduce file contention during local testing.
- **Concurrency Limitation Warning**: SQLite uses file-level locking and does NOT support row-level locks (`SELECT FOR UPDATE`). SQLite cannot provide PostgreSQL-equivalent concurrency guarantees. It is strictly for development and testing.

### 3.2 PostgreSQL 16+ Required for Production
- Production requires PostgreSQL 16+ to handle high concurrent booking attempts and checkout holds safely.
- PostgreSQL provides true row-level locking (`select_for_update()`) inside atomic transactions, guaranteeing that two customers cannot hold or book the last available room simultaneously.

### 3.3 Portability Rules Enforced:
1. **ANSI-SQL & Django ORM Compliance**: Zero raw DB-specific SQL dialect tricks.
2. **Explicit Decimal Precisions**: All financial currency values use `DecimalField(max_digits=12, decimal_places=2)`. Never use `FloatField`.
3. **UTC Timestamps Everywhere**: `USE_TZ = True`, all datetime fields use `DateTimeField(auto_now_add=True)` or `DateTimeField()`.
4. **Secure Public Identifiers**: All customer-facing references use UUID4 or secure alphanumeric reference codes (`MG-YYYYMMDD-XXXX`) to prevent ID enumeration. Public confirmation lookup requires a secure access token.
5. **Standard Indexing**: Portable `models.Index(fields=['field1', 'field2'])`.

## 4. Unified Inventory Principle
Online customer direct bookings, walk-in reservations, phone bookings, WhatsApp inquiries, and corporate bulk bookings draw from the **SAME authoritative 28 physical rooms**.
- There is **no separate online inventory pool** and **no separate offline inventory pool**.
- Every confirmed booking, front-desk walk-in, or maintenance block immediately decrements the single unified availability seen across all channels.

## 5. CLIENT-CONFIRMED BUSINESS RULES (Baseline for Future Phases)

The following business rules have been confirmed by the client and form the authoritative business baseline:

1. **Room Inventory & Unified Multi-Channel System**: 28 total physical rooms (20 AC, 8 Non-AC). All channels (Online direct, Front-desk walk-in, Phone, WhatsApp) share the exact same physical room inventory.
2. **Room Pricing (Authoritative & Configurable)**:
   - AC Room: ₹1,599 / night
   - Non-AC Room: ₹1,299 / night
   - Rates are managed dynamically via backend settings/database and retrieved via API.
3. **Extra Occupant Charges**:
   - Extra Adult: ₹350 / night
   - Extra Child: ₹300 / night
4. **Taxes (GST)**: Current baseline = 5% (configured centrally in `TaxRule`).
5. **Check-In & Check-Out Timings**:
   - Standard Check-In: 11:00 AM
   - Standard Check-Out: 11:00 AM next day (24-hour stay concept)
6. **Late Check-Out Surcharges**:
   - AC Room: ₹150 / hour
   - Non-AC Room: ₹100 / hour
   - Allowed up to 3 hours past standard checkout (11:00 AM to 2:00 PM). Beyond 3 hours, a full extra night is charged.
7. **Cancellation & Refund Policy**:
   - Confirmed bookings are strictly non-refundable (0% refund).
   - Same-day cancellations: 0% refund.
8. **Payment Terms (Split Advance)**:
   - Online Direct: 50% advance deposit via Razorpay required to confirm booking.
   - Remaining 50% balance must be paid at front desk before check-in.
   - Server-side Razorpay verification is authoritative.
9. **Admin Overbooking Override**:
   - Owner/SuperAdmin may explicitly override room availability when fully booked with mandatory audit logging.
10. **Admin Roles & Permissions**:
    - `SUPER_ADMIN` (Owner): Full access (pricing, inventory, bookings, staff, reports, CMS, overbooking override).
    - `MANAGER`: Partial operational management.
    - `RECEPTIONIST`: Front-desk operations (bookings, check-in, check-out, physical room assignment).
11. **Physical Room Assignment**:
    - Guests reserve a category (e.g. AC Room). Staff assign specific physical room (e.g. Room 105) prior to or at check-in.
12. **Aadhaar / Guest ID Verification**:
    - Guests provide Aadhaar photo/copy. Files stored in private authenticated storage with strict staff-only access and audit trails. (Scheduled for future phase).

### UNRESOLVED CLIENT QUESTION
- **Non-AC Maximum Occupancy**: Client explicitly stated "2 PAX only" but in an example noted "Non-AC Room → maximum 3 guests".
- **Current Working Baseline**: 2 PAX (pending formal client clarification). AC Room is confirmed at 4 PAX maximum. Max occupancy limits are not freely editable by admins.
