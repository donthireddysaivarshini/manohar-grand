# Availability Engine & Hotel Night Calculation Engine

## 1. Hotel-Standard Night Consumption Rules

The system implements the global hospitality standard for date handling:
- **Stay Dates**: Defined by `check_in_date` and `check_out_date`.
- **Night Set ($N$)**: The set of dates consumed as overnight stays:
  $$N = \{ d \in \text{Dates} \mid \text{check\_in\_date} \le d < \text{check\_out\_date} \}$$
- **Check-Out Date Rule**: The check-out date is **never** consumed as an overnight stay. Standard check-out is 11:00 AM and standard check-in is 11:00 AM (client-confirmed 24-hour stay concept). A guest checking out on 13th October vacates the room by 11:00 AM, allowing turnaround for a new check-in arriving on 13th October at 11:00 AM onwards.

```
Example: Check-In = 10 Oct 2026 (11:00 AM), Check-Out = 13 Oct 2026 (11:00 AM)
Consumed Nights = [10 Oct, 11 Oct, 12 Oct] (Total: 3 Nights)
```

## 2. Authoritative Category Availability Algorithm

Availability is derived dynamically from **Active Physical Rooms** rather than an editable static counter:

### 2.1 Baseline Capacity ($T_C$)
For any category $C$ (AC Room or Non-AC Room):
$$T_C = \text{Count}(\text{PhysicalRoom where category}=C \text{ and is\_active}=\text{True and status}=\text{'active'})$$
*(Confirmed baseline: 20 AC Physical Rooms, 8 Non-AC Physical Rooms).*

### 2.2 Unified Occupancy Calculation ($O(C, d)$)
For every night $d \in [D_{in}, D_{out})$:
1. **Active Bookings & Holds**: Count of rooms booked or currently held across both online and offline channels:
   $$B(C, d) = \text{Count}(\text{BookingRoom where category}=C \text{ and booking covers night } d \text{ and status} \in \{\text{'confirmed', 'checked\_in', 'valid\_hold'}\})$$
   *(Note: Holds with `hold_expires_at < now()` are excluded automatically).*
2. **Maintenance / Admin Blocks**: Count of physical rooms in category $C$ with an active block covering night $d$:
   $$M(C, d) = \text{Count}(\text{RoomBlock where physical\_room.category}=C \text{ and block covers night } d)$$
3. **Total Occupied Rooms**:
   $$O(C, d) = B(C, d) + M(C, d)$$
4. **Available Rooms on Night $d$**:
   $$A(C, d) = T_C - O(C, d)$$

### 2.3 Bottleneck Stay Availability
The **maximum bookable rooms** for the requested stay $(D_{in}, D_{out})$ is the **minimum available capacity** across all consumed nights:
$$\text{BookableRooms}(C, D_{in}, D_{out}) = \min_{d \in [D_{in}, D_{out})} A(C, d)$$

```
Example (20 Total Physical AC Rooms):
- 10 Oct: 10 occupied (8 confirmed + 2 reception walk-ins) -> 10 available
- 11 Oct: 12 occupied (9 confirmed + 2 walk-ins + 1 maintenance block) -> 8 available
- 12 Oct: 5 occupied (5 confirmed) -> 15 available

Result for 10–13 Oct Stay = min(10, 8, 15) = 8 AC Rooms Bookable
```

## 3. Alternative Date & Category Recommendations

When a customer searches for dates or quantities that exceed availability:
1. **Alternative Room Categories**: The API checks availability for the other category (e.g. Non-AC Room) for the exact requested dates.
2. **Alternative Date Windows**: The engine evaluates $\pm 3$ days surrounding the requested window and recommends nearest available dates.
3. **Split Category Combinations**: If a customer requests 3 rooms and only 2 AC are available, the API suggests booking 2 AC + 1 Non-AC.
