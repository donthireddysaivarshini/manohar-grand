# Availability Engine & Hotel Night Calculation Engine

## 1. Hotel-Standard Night Consumption Rules

The system implements the global hospitality standard for date handling:
- **Stay Dates**: Defined by `check_in_date` and `check_out_date`.
- **Night Set ($N$)**: The set of dates consumed as overnight stays:
  $$N = \{ d \in \text{Dates} \mid \text{check\_in\_date} \le d < \text{check\_out\_date} \}$$
- **Check-Out Date Rule**: The check-out date is **never** consumed as an overnight stay. Standard check-out is 11:00 AM and standard check-in is 11:00 AM (client-confirmed 24-hour stay concept). A guest checking out on 13th October vacates the room by 11:00 AM, allowing turnaround for a new check-in arriving on 13th October at 11:00 AM onwards.

```
Example: Check-In = 10 Oct 2026 (11:00 AM), Check-Out = 13 Oct 2026 (11:00 AM)
Consumed Nights = [10 Oct, 11 Oct, 12 Oct] (Total: 3 Nights)
```

## 2. Authoritative Category Availability Algorithm (`apps.availability.services.AvailabilityService`)

Availability is derived dynamically from **Active Physical Rooms** rather than an editable static counter:

### 2.1 Baseline Capacity ($T_C$)
For any active category $C$ (`is_active=True`):
$$T_C = \text{Count}(\text{PhysicalRoom where category}=C \text{ and operational\_status}=\text{'operational'})$$
*(If category is inactive, $T_C = 0$ and availability is 0).*

### 2.2 Unified Occupancy Calculation ($O(C, d)$)
For every night $d \in [D_{in}, D_{out})$:
1. **Active Bookings & Holds ($B(C, d)$)**:
   Sum of `BookingRoom.room_quantity` for bookings covering night $d$ (`check_in <= d < check_out`) with:
   - `status` in `['confirmed', 'checked_in']` OR
   - `status == 'held'` AND `hold_expires_at > timezone.now()` (dynamically excluding expired holds).
   *(Note: Physical room assignment is operational front-desk data and does not cause double-counting).*

2. **Dated Operational Blocks ($D(C, d)$)**:
   Count of distinct operational physical rooms affected by active `RoomBlock` or `MaintenanceBlock` on night $d$:
   $$\text{BlockedRooms}_{C, d} = \{ \text{physical\_room\_id} \mid \text{active block covers night } d \}$$
   $$D(C, d) = |\text{BlockedRooms}_{C, d} \cap \text{OperationalRooms}_C|$$
   *(Overlapping blocks on the same physical room are deduplicated via set union).*

3. **Available Rooms on Night $d$**:
   $$A(C, d) = \max(0, T_C - D(C, d) - B(C, d))$$

### 2.3 Bottleneck Stay Availability
The **maximum bookable rooms** for the requested stay $(D_{in}, D_{out})$ is the **minimum available capacity** across all consumed nights:
$$\text{StayAvailability}(C, D_{in}, D_{out}) = \min_{d \in [D_{in}, D_{out})} A(C, d)$$

## 3. Concurrency Boundary & Production Lock Semantics
The availability search endpoint (`GET /api/v1/availability/search/`) is an uncommitted, read-only calculation providing current capacity. In production, atomic hold and reservation creation in Step 3 will re-verify availability inside a `@transaction.atomic` block using PostgreSQL row-level locks (`select_for_update()`) on target `RoomCategory` rows.
