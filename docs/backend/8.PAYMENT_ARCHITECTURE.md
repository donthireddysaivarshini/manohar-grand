# Payment Architecture & Razorpay Integration Design

> [!IMPORTANT]
> **Phase Notice**: This document details the future payment architecture for **Phase 5**. Razorpay APIs and payment verification must **NOT** be implemented in Phase 1.

## 1. End-to-End Payment Flow

The payment system coordinates securely between the customer client, Django backend, and the Razorpay gateway. The client is **never trusted** as proof of payment.

```
Customer Client             Django Backend (/api/v1/)              Razorpay Gateway
     |                                 |                                  |
     | 1. POST /bookings/hold/         |                                  |
     |-------------------------------->|                                  |
     |                                 | 2. Create Order in Razorpay      |
     |                                 |    (Server-calculated amount)    |
     |                                 |--------------------------------->|
     |                                 | 3. Returns order_id & amount     |
     |                                 |<---------------------------------|
     | 4. Returns razorpay_order_id    |                                  |
     |<--------------------------------|                                  |
     |                                 |                                  |
     | 5. Launch Razorpay Checkout Modal (UPI, Cards, NetBanking)         |
     |------------------------------------------------------------------->|
     |                                 |                                  |
     | 6. User Completes Payment       |                                  |
     |<-------------------------------------------------------------------|
     |                                 |                                  |
     | 7. POST /payments/verify/       |                                  |
     |    (order_id, payment_id, sig)  |                                  |
     |-------------------------------->| 8. Verify Ownership & Signature  |
     |                                 |    (Validates All 6 Checkpoints) |
     |                                 | 9. Update Booking -> CONFIRMED   |
     |                                 | 10. Update Inventory Permanent   |
     | 11. Confirmed Booking Voucher   |                                  |
     |<--------------------------------|                                  |
     |                                 |                                  |
     |                                 | 12. Idempotent Async Webhook     |
     |                                 |<---------------------------------|
     |                                 | (payment.captured / refund.proc) |
```

## 2. Mandatory Backend Payment Verification Checkpoints

When the frontend submits payment details for verification at `POST /api/v1/payments/verify/`, the backend **must validate all of the following at minimum**:

1. **Booking Ownership / Session**: The booking belongs to the currently authenticated customer or matches the secure checkout session.
2. **Booking Status**: The booking is currently in `HELD` status and `hold_expires_at > timezone.now()`. (Expired holds cannot be confirmed).
3. **Authoritative Server-Side Amount**: The amount billed in Razorpay exactly matches the authoritative `advance_amount_due` (50% deposit) stored in `BookingPriceSnapshot` (converted to paise). The frontend amount is completely ignored.
4. **Razorpay Order ID Consistency**: The `razorpay_order_id` matches the active `PaymentOrder` record linked to the booking in the database.
5. **Razorpay Payment ID Presence**: The `razorpay_payment_id` is present, valid, and not already associated with another completed booking.
6. **Cryptographic HMAC-SHA256 Signature**: The signature generated matches `HMAC_SHA256(order_id + "|" + payment_id, RAZORPAY_KEY_SECRET)`.

```python
import hmac
import hashlib

def verify_payment_authenticity(booking, razorpay_order_id, razorpay_payment_id, signature, secret):
    # 1. Status & Hold Expiration Check
    if booking.status != 'held' or booking.hold_expires_at < timezone.now():
        raise InvalidBookingStateException("Hold has expired or booking is not in held state.")
        
    # 2. Order ID Verification
    payment_order = booking.payment_orders.filter(razorpay_order_id=razorpay_order_id).first()
    if not payment_order:
        raise SecurityValidationException("Order ID mismatch.")
        
    # 3. Cryptographic Signature Validation
    payload = f"{razorpay_order_id}|{razorpay_payment_id}".encode('utf-8')
    expected_sig = hmac.new(
        secret.encode('utf-8'),
        payload,
        hashlib.sha256
    ).hexdigest()
    
    if not hmac.compare_digest(expected_sig, signature):
        raise SignatureMismatchException("Cryptographic payment signature verification failed.")
        
    return True
```

## 3. Idempotent Webhook Processing

- Razorpay dispatches asynchronous webhooks (`payment.captured`, `payment.failed`, `refund.processed`).
- The backend tracks processed events in `WebhookEventLog(event_id=..., processed=True)`.
- If a webhook retry arrives for an already processed event, the backend acknowledges with HTTP 200 OK without double-processing or mutating state twice.

---

## 4. CLIENT-CONFIRMED PAYMENT TERMS BASELINE

1. **Payment Gateway**: Razorpay is confirmed for online payments (UPI, Cards, NetBanking).
2. **Deposit Requirement**: Online reservations require **50% advance payment** via Razorpay to transition from `HELD` to `CONFIRMED`.
3. **Balance Collection**: Remaining **50% balance** is due at the hotel front desk prior to check-in / room key handover.
4. **Front-Desk Payment Methods**: Cash, POS Card, POS UPI, or Bank Transfer.
5. **Authoritative State**: Payment status is tracked independently from booking status in `PaymentTransaction` records. Never trust frontend "payment successful" events.
