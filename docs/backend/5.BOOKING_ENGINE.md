# Booking Engine Architecture & Reservation Lifecycle

## 1. Booking State Machine

Every reservation transitions through a strictly defined lifecycle to guarantee inventory integrity and prevent orphaned locks:

```
                  [ Customer Initiates Checkout ]
                                 |
                                 v
                            +---------+
                            |  HELD   |  (Configurable: Default 15-Minute Lock)
                            +----+----+
                                 |
              +------------------+------------------+
              | (Payment Success / Confirmed)       | (Timeout / Cancelled / Payment Failed)
              v                                     v
       +-------------+                       +-------------+
       |  CONFIRMED  |                       |   EXPIRED   |
       +------+------+                       | (Lock Freed)|
              |                              +-------------+
              | (Guest Arrives at Hotel)
              v
       +--------------+
       |  CHECKED_IN  |  (Physical Room Number Assigned)
       +------+-------+
              |
              | (Check-out Date)
              v
       +---------------+
       |  CHECKED_OUT  |  (Completed Stay)
       +---------------+
              ^
              | (If Cancelled via Policy)
       +---------------+
       |   CANCELLED   |  (Inventory Instantly Restored)
       +---------------+
```

## 2. Configurable Temporary Inventory Hold Mechanism

### Problem:
When a customer proceeds to checkout, the requested room category must be temporarily held to prevent simultaneous double-booking. If the customer closes the tab or abandons payment, the rooms must automatically release without manual staff intervention.

### Solution Architecture:
1. **Hold Duration**:
   - Initial setting: **15 minutes** (Configured via `BOOKING_HOLD_DURATION_MINUTES = 15` in Django settings, editable via system configuration).
2. **Hold Initiation**:
   - `POST /api/v1/bookings/hold/`
   - Atomically checks availability against active `PhysicalRoom` records across every night of the stay.
   - Creates a `Booking` in `status='held'` with `hold_expires_at = now() + timedelta(minutes=BOOKING_HOLD_DURATION_MINUTES)`.
   - Generates a secure `booking_reference` and an unguessable `access_token` (UUID4).
3. **Hold Expiry & Invalidation**:
   - **Lazy Invalidation**: Any availability calculation query automatically ignores bookings where `status='held'` AND `hold_expires_at < timezone.now()`. Expired rooms become immediately bookable by other customers without waiting for background jobs.
   - **Periodic Background Cleanup**: A lightweight task runs every 60 seconds marking expired holds as `status='expired'`.
4. **Hold Conversion on Successful Payment**:
   - Upon cryptographic payment verification, the booking state transitions from `HELD` to `CONFIRMED`, permanently securing the reservation and clearing `hold_expires_at`.

## 3. Unified Inventory & Concurrency Protection

Online direct bookings, front-desk walk-ins, phone reservations, and corporate bulk bookings operate on the **SAME 28 physical rooms**.

```python
# Authoritative Atomic Availability Check & Hold Creation
@transaction.atomic
def create_reservation_hold(category_id, check_in, check_out, requested_rooms_count, customer=None, source='online_direct'):
    # 1. Lock category & physical rooms in PostgreSQL (select_for_update)
    category = RoomCategory.objects.get(id=category_id)
    total_physical_rooms = PhysicalRoom.objects.filter(
        category=category, 
        is_active=True, 
        status='active'
    ).count()
    
    # 2. Inspect every night in the consumed range [check_in, check_out)
    stay_nights = get_stay_nights(check_in, check_out)
    
    for night in stay_nights:
        # Count occupied rooms: confirmed + unexpired holds + maintenance blocks
        active_holds_and_bookings = BookingRoom.objects.filter(
            category=category,
            booking__check_in_date__lte=night,
            booking__check_out_date__gt=night,
            booking__status__in=['confirmed', 'checked_in', 'held']
        ).exclude(
            booking__status='held',
            booking__hold_expires_at__lt=timezone.now() # Exclude expired holds
        ).count()
        
        maintenance_blocks = RoomBlock.objects.filter(
            physical_room__category=category,
            start_date__lte=night,
            end_date__gt=night
        ).count()
        
        occupied_count = active_holds_and_bookings + maintenance_blocks
        available_rooms = total_physical_rooms - occupied_count
        
        if available_rooms < requested_rooms_count:
            raise InventoryExhaustedException(
                f"Insufficient inventory on {night}. Available: {available_rooms}, Requested: {requested_rooms_count}"
            )
            
    # 3. Create the Booking & BookingRoom records atomically
    booking = Booking.objects.create(
        customer=customer,
        source=source,
        status='held',
        check_in_date=check_in,
        check_out_date=check_out,
        nights_count=len(stay_nights),
        total_rooms_count=requested_rooms_count,
        hold_expires_at=timezone.now() + timedelta(minutes=settings.BOOKING_HOLD_DURATION_MINUTES),
        access_token=uuid.uuid4(),
        ...
    )
    for index in range(requested_rooms_count):
        BookingRoom.objects.create(
            booking=booking,
            category=category,
            room_index=index + 1
        )
        
    return booking
```

## 4. Offline / Admin-Created Bookings

Authorized front desk receptionists and hotel managers can create offline bookings directly from the admin panel:
- **Booking Sources**: `walk_in` (Front desk walk-in), `phone` (Phone call inquiry), `whatsapp_direct`, `corporate` (Bulk deal).
- **Inventory Impact**: Admin-created bookings deduct immediately from the single unified availability matrix.
- **Payment Methods Supported**: Cash (`cash`), Card POS (`pos_card`), UPI Terminal (`pos_upi`), Direct Bank Transfer (`bank_transfer`), or Pay-at-Hotel (`pay_at_hotel`).
- **Physical Room Assignment**: Receptionists can either assign physical room numbers immediately at creation or keep them category-allocated until check-in.
- **Permissions**:
  - `receptionist`: Can create walk-in/phone bookings, collect payments, and assign physical rooms.
  - `manager` / `superadmin`: Can create corporate deals, apply custom negotiated tariffs, cancel bookings, and approve refunds.
- **Admin Overbooking / Override Rule (Client-Confirmed)**:
  - The Owner / `SUPER_ADMIN` can explicitly override room availability when fully booked to create an additional booking.
  - This action requires explicit permission, creates an audit record capturing the staff user ID, timestamp, and justification, and is distinctly flagged in reporting.

## 5. Physical Room Assignment Workflow

1. **Initial Booking**: The customer or front desk initially reserves a **Room Category** (e.g. 1 AC Room).
2. **Room Allocation**: Prior to or upon guest check-in, the receptionist uses the Admin Console to assign a specific physical unit (e.g., `Room 105`).
3. **Validation**: The backend verifies:
   - The selected physical room belongs to the reserved category.
   - The physical room is `is_active=True` and `status='active'`.
   - The physical room is not already assigned to another overlapping active reservation or maintenance block.

---

## 6. Secure Public Booking Lookup
- **Security Rule**: Public guests cannot view complete reservation details or guest PII simply by guessing a `booking_reference`.
- **Lookup Mechanism**:
  - Authenticated customers view their booking history securely via their authenticated session.
  - Unauthenticated public confirmation queries require both the `booking_reference` AND the cryptographic `access_token` issued upon booking creation (`GET /api/v1/bookings/{reference}/?token={access_token}`).
