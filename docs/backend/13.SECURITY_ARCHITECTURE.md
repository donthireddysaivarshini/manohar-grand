# Security Architecture & Hardening Specifications

## 1. Overview
The security model for the **Manohar Grand Direct Booking Platform** enforces defense-in-depth across the API gateway, session/auth layer, business logic (booking engine, payments), and data storage layer.

---

## 2. Authentication & Authorization Security

### 2.1 Google OAuth2 Customer Authentication
- Customer Google Sign-In utilizes standard Django social-auth (`django-allauth`) with the Google OAuth 2.0 provider.
- Google OAuth credentials (`GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`) are provided via environment variables and loaded into Django settings / Django admin `SocialApp` configurations.
- **Tokens are validated server-side** against Google's authentication servers. Client-provided email or user IDs are never trusted without cryptographically valid server verification.
- Upon successful exchange, the backend issues an internal, secure, HttpOnly session cookie (`sessionid`). The Google token is **never** used as the long-lived application session.

### 2.2 Staff Authentication & RBAC
- Dedicated `/api/v1/auth/login/` for staff accounts using PBKDF2/Argon2 password hashing.
- Endpoints under `/api/v1/admin/` enforce role permission classes (`IsAdminUser`, `HasRolePermission`).
- Customer access to booking history strictly filters by `request.user` (`queryset.filter(user=request.user)`), preventing Insecure Direct Object References (IDOR).
- Public unauthenticated confirmation queries require both the `booking_reference` AND the cryptographic `access_token` issued at booking creation.

### 2.3 Session Security & Cookies
- `SESSION_COOKIE_HTTPONLY = True` (Mitigates XSS extraction).
- `SESSION_COOKIE_SECURE = True` (Enforced in production HTTPS).
- `SESSION_COOKIE_SAMESITE = 'Lax'`.
- `SESSION_COOKIE_AGE = 1209600` (14 days for customer session, 8 hours for Staff/Admin).

## 3. Network & Transport Security

### 3.1 CORS (Cross-Origin Resource Sharing)
- `django-cors-headers` configured with explicit whitelist:
  - `CORS_ALLOWED_ORIGINS = ["https://manohargrand.com", "https://admin.manohargrand.com"]` (Local dev: `["http://localhost:5173"]`).
  - `CORS_ALLOW_CREDENTIALS = True` to support cookie-based sessions.
  - Wildcard `CORS_ALLOW_ALL_ORIGINS = True` is **strictly forbidden**.

### 3.2 CSRF Protection
- For session-authenticated state-modifying requests (POST, PUT, PATCH, DELETE), Django's CSRF middleware validates the `X-CSRFToken` header.
- `CSRF_COOKIE_HTTPONLY = False` allows frontend client JS to read the CSRF cookie token and attach it to API request headers.

### 3.3 Rate Limiting / Throttling
Django REST Framework throttling tiers:
- **AnonThrottle**: 60 requests / minute (search & availability browse).
- **UserThrottle**: 300 requests / minute.
- **Strict Endpoint Throttling**:
  - `/api/v1/auth/google/` & `/api/v1/auth/login/`: 5 attempts / minute per IP.
  - `/api/v1/bookings/hold/`: 10 requests / minute per IP/User (prevents inventory locking Denial-of-Service).
  - `/api/v1/payments/verify/`: 10 requests / minute.

## 4. Payment & Financial Data Security (Designed for Phase 5)

### 4.1 Payment Gateway Protection (Razorpay)
- **Zero Cardholder Data Storage**: No credit card, debit card, UPI PIN, or CVV ever touches the Manohar Grand backend. All PCI-DSS scope is offloaded to Razorpay's PCI-DSS Level 1 compliant checkout modal.
- **HMAC-SHA256 Signature Verification**:
  - Signatures verified using `razorpay_order_id`, `razorpay_payment_id`, and `RAZORPAY_KEY_SECRET`.
  - Webhooks verified using `X-Razorpay-Signature` and `RAZORPAY_WEBHOOK_SECRET`.
- **Idempotent Webhook Handling**:
  - Webhook payloads logged and deduplicated via `WebhookEventLog(event_id, processed=True)` to prevent duplicate capture or double-refund exploits.

## 5. PII & Guest Privacy (Physical Verification vs Digital Aadhaar)

### 5.1 Government ID Handling (Aadhaar Rule)
- Primary guest and additional adult guests must furnish original Government Photo ID (Aadhaar / Passport / Voter ID / Driving License) upon check-in at hotel reception (primary guest 18+).
- **Digital Storage Excluded**: Digital Aadhaar numbers or image scans are marked as `UNKNOWN — CLIENT CONFIRMATION REQUIRED` and are **NOT stored**.
- **Metadata Only**: The system stores only front-desk verification metadata (`identity_type`, `verification_status`, `verified_by`, `verified_at`).

## 6. Audit Logging & Secrets Management

### 6.1 Audit Trail
- All administrative mutations (rate modifications, room blocks, manual booking cancellations, refund executions, user role changes) generate immutable records in `AuditLog`.
- Fields recorded: `actor_id`, `action`, `target_model`, `target_id`, `ip_address`, `user_agent`, `changes_json`, `created_at`.

### 6.2 Environment & Secrets Management
- All secrets, API keys, database credentials, and signing secrets managed strictly via `.env` / environment variables.
- `.env` excluded from version control (`.gitignore`).
